## Мысленная модель

ComfyUI MCP — тонкий, хорошо описанный слой над **работающим экземпляром
ComfyUI**. Большинство инструментов говорит с этим экземпляром через его
HTTP/WebSocket API, поэтому они работают одинаково, локальный ли ComfyUI,
удалённый (`--comfyui-url`) или [Comfy Cloud](https://cloud.comfy.org)
(`COMFYUI_API_KEY`).

<Steps>
  <Step title="Генерация и воркфлоу → HTTP API ComfyUI">
    `generate_image`, `enqueue_workflow`, очередь/история/системная статистика и
    инструменты создания воркфлоу вызывают `/prompt`, `/queue`, `/history`,
    `/object_info` ComfyUI и т. д. Постановка в очередь — fire-and-forget: вы
    сразу получаете `prompt_id`, а результаты приходят уведомлением о завершении.
    В облачном режиме альтернативный `cloud-client` направляет те же операции на
    `cloud.comfy.org` через `X-API-Key`.
  </Step>
  <Step title="Кастомные узлы и модели → ComfyUI-Manager (HTTP), с запасным subprocess">
    Установка/обновление/снимки/bisect узлов и установка зависимостей воркфлоу
    предпочитают HTTP API [ComfyUI-Manager](https://github.com/Comfy-Org/ComfyUI-Manager)
    (поэтому работают и против удалённых экземпляров), с откатом на `cm-cli` /
    `git` / `pip`/`uv` против локальной установки там, где API не справляется.
  </Step>
  <Step title="Установка и операции с файловой системой → только локально">
    Установка ComfyUI, обновление ядра, удаление файлов моделей, чтение логов
    сервера и список каталога вывода работают с локальной файловой системой. Им
    нужен известный `COMFYUI_PATH`, и в удалённом или облачном режиме они
    возвращают понятную ошибку.
  </Step>
  <Step title="WebSocket → локально + удалённо, не облако">
    Уведомления о завершении заданий подключаются к WebSocket ComfyUI, где он
    есть. У Comfy Cloud нет WebSocket — наблюдатель заданий проваливается на
    уже существующий путь HTTP-опроса.
  </Step>
</Steps>

<Note>
  Правило большого пальца: всё, что **читает или запускает** подключённый
  сервер, работает в любом режиме; всё, что **ставит ПО или трогает файлы на
  диске**, нуждается в локальной установке. Полная матрица соответствия
  возможностей — в [Настройки → Режимы развёртывания](/docs/ru/configuration#режимы-развёртывания).
</Note>

## Самолечение: сторожевой таймер очереди/рендера

Заклинивший шаг сэмплера высокого разрешения раньше позволял агенту складывать
задания за зомби-рендером, который он не видел и не мог убить. Три защиты по
мере возможности закрывают этот пробел, чтобы агент перестал вслепую ставить
новое за застрявшим рендером:

- **Обратное давление** — `panel_run` дописывает QUEUE WARNING к результату,
  когда рендер уже идёт, чтобы агент не складывал за ним.
- **Обнаружение зависания** — пассивный WebSocket к ComfyUI отслеживает
  текущий промпт / узел / прогресс; шаг, который перестал продвигаться дольше
  порога
  ([`COMFYUI_MCP_STALL_S`](/docs/ru/configuration#оркестратор-панели-и-мост),
  по умолчанию 180 с), предваряет следующую реплику агента однострочной
  заметкой STALL/BACKLOG.
- **Эскалирующая отмена** — `queue` (action:"cancel") прерывает, **проверяет**,
  что задание действительно остановилось
  (в пределах [`COMFYUI_MCP_INTERRUPT_S`](/docs/ru/configuration#наблюдение-за-заданиями),
  по умолчанию 30 с), затем эскалирует к `/free` и сообщает, что рендер WEDGED
  (предлагая `restart_comfyui`), если он всё ещё не умирает; `clear_pending`
  сбрасывает все ожидающие задания в том же вызове.

Всё fail-safe: если сторожевой WebSocket так и не открылся, ничего не меняется.
Агент также может рассуждать о цветах изображения без круга vision через
`get_image (action:"analyze_color")`
(доминирующая палитра, средняя + статистика яркости, проверки контраста).
